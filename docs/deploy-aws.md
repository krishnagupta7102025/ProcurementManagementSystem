# Deploying: AWS (Elastic Beanstalk + RDS MySQL + S3 + CloudFront)

Decided 2026-09-25, after GitHub Pages/Render and Vercel both ran into
platform-specific dead ends (see [deploy-github-pages-render.md](deploy-github-pages-render.md)
and [deploy-vercel.md](deploy-vercel.md), both now superseded). This also
coincides with switching the database from PostgreSQL to MySQL — see the
Decisions Log in [00-prd.md](00-prd.md) §12.

| Piece                        | Service                                                    |
| ----------------------------- | ----------------------------------------------------------- |
| API compute                  | Elastic Beanstalk, Docker platform, single instance         |
| Database                     | RDS MySQL 8                                                  |
| Document storage              | S3 (private — API reads/writes via its instance role)       |
| Frontend static hosting        | S3 (private) + CloudFront                                    |
| API HTTPS termination          | A second CloudFront distribution in front of the same EB environment (see "Why two CloudFront distributions" below) |
| Approval-SLA escalation job    | EventBridge Scheduler, every 15 minutes                     |
| Docker image registry          | ECR                                                          |

All of this is defined in [infra/aws/](../infra/aws/) as Terraform. **This
Terraform has not been run or validated against a live AWS account or even
`terraform validate`** — there's no `terraform` binary in the environment
this was written in. Treat it as a solid first draft: run `terraform init &&
terraform validate && terraform plan` yourself and be ready to fix small
things (the most likely one: `eb_solution_stack_name` in
[variables.tf](../infra/aws/variables.tf) — AWS revises these strings
periodically; the comment there shows how to look up the current one).

## Why two CloudFront distributions

The frontend is a static export served over HTTPS via CloudFront. The API
runs on a **SingleInstance** Elastic Beanstalk environment (no load
balancer, chosen to keep this cheap and simple) — which means it only
speaks plain HTTP on its own `*.elasticbeanstalk.com` domain. A browser
`fetch()` from the HTTPS frontend straight to that HTTP API would be
blocked as mixed content. Standing up a load balancer + a real domain + an
ACM certificate just to get HTTPS on the API would work, but is a lot of
extra moving parts for a first deployment. Putting a second, API-only
CloudFront distribution in front of the same EB environment gets free
HTTPS on CloudFront's own domain for the cost of one extra resource, with
CloudFront-to-EB traffic staying as a plain-HTTP hop inside AWS (not
browser-facing, so no mixed-content concern there).

## 0. Prerequisites

- AWS CLI configured (`aws configure`) with credentials that can create
  RDS/EB/S3/CloudFront/IAM/ECR/EventBridge resources
- Terraform >= 1.7
- Docker, for building the API's image

## 1. Provision the infrastructure

```bash
cd infra/aws
terraform init

# First, create just the ECR repo — the bootstrap Elastic Beanstalk
# application version needs an image to already exist at that repo's
# ":latest" tag before the environment can come up healthy.
terraform apply -target=aws_ecr_repository.api
```

Build and push the API's Docker image (from the **repo root**, not
`apps/api/` — the Dockerfile needs the pnpm workspace files):

```bash
cd ../..   # back to repo root
REPO_URL=$(cd infra/aws && terraform output -raw ecr_repository_url)
aws ecr get-login-password --region ap-south-1 | docker login --username AWS --password-stdin "${REPO_URL%%/*}"
docker build -f apps/api/Dockerfile -t "$REPO_URL:latest" .
docker push "$REPO_URL:latest"
```

Now provision everything else:

```bash
cd infra/aws
terraform apply
```

This creates the RDS instance, the S3 buckets, both CloudFront
distributions, the Elastic Beanstalk application/environment (pulling the
image you just pushed), and the EventBridge Scheduler rule. Expect this to
take 10-15 minutes — RDS and CloudFront are both slow to provision.

Every secret the app needs (`AUTH_JWT_SECRET`, `CRON_SECRET`, the RDS
password) is generated by Terraform and wired directly into the EB
environment's variables — there's no manual env var entry step like the
Vercel/Render deploys needed.

**Migrations run themselves.** `apps/api/Dockerfile`'s `CMD` already runs
`prisma migrate deploy` before starting the server, on every container
boot — since the container runs inside the EB environment (same VPC/
security-group path to RDS), there's no separate "run migrations from your
laptop" step, and RDS is deliberately not publicly reachable
(`publicly_accessible = false` in `rds.tf`) so this is the only path in.

**Seed data is optional and demo-only**, same caveat as every other
environment: `pnpm --filter api run db:seed` creates 7 users sharing the
password `Passw0rd!`. If you want to run it against the real RDS database,
the instance isn't publicly reachable, so do it from inside the VPC — e.g.
temporarily add your IP to `aws_security_group.rds` and set
`publicly_accessible = true`, run the seed script with `DATABASE_URL`
pointed at the RDS endpoint, then revert both. Never do this against an
environment with real data.

## 2. Check the outputs

```bash
terraform output
```

- `api_url` — the API's public HTTPS URL (via CloudFront). This is
  `NEXT_PUBLIC_API_URL` for the frontend.
- `cloudfront_domain_name` — the frontend's public URL.
- `eb_environment_url` — the API's raw HTTP URL, useful for direct
  debugging (`curl` health checks) but not for the frontend to call.

## 3. Deploy the frontend

```bash
cd apps/web
NEXT_PUBLIC_API_URL=$(cd ../../infra/aws && terraform output -raw api_url) pnpm run build
aws s3 sync out/ "s3://$(cd ../../infra/aws && terraform output -raw frontend_bucket_name)/" --delete
aws cloudfront create-invalidation \
  --distribution-id "$(cd ../../infra/aws && terraform output -raw cloudfront_distribution_id)" \
  --paths "/*"
```

(`out/` is the static export's output directory — see `next.config.ts`'s
`output: 'export'`.)

## 4. Verify

1. Visit `cloudfront_domain_name` — should redirect to `/login`.
2. Log in (seeded demo accounts, if you seeded: `admin@demo.p2p` /
   `Passw0rd!`).
3. If login fails with a network error, open the browser's Network tab and
   check the request actually went to the `api_url` domain, not
   `localhost` or the raw `eb_environment_url` — a stale frontend build
   (before `NEXT_PUBLIC_API_URL` was set) is the most common cause, same
   failure mode as the earlier Vercel deploys had.

## Redeploying after a code change

**API** — rebuild and push a new `:latest` image, then tell the running
environment to pull it:

```bash
docker build -f apps/api/Dockerfile -t "$REPO_URL:latest" .
docker push "$REPO_URL:latest"
aws elasticbeanstalk restart-app-server --environment-name p2p-api-production
```

(Terraform doesn't need to run again for a routine app deploy — it only
owns the bootstrap version and the surrounding infrastructure.)

**Frontend** — repeat step 3 above.

## What's simplified here, worth revisiting before this holds real production traffic

- **Default VPC, single-AZ RDS, SingleInstance EB** — cheap and simple, not
  the multi-AZ HA setup CLAUDE.md originally described. `db_multi_az` and
  the EB `EnvironmentType` setting are the two knobs to flip when that
  matters.
- **No custom domain** — everything lives on `*.cloudfront.net` /
  `*.elasticbeanstalk.com`. `variables.tf` has `frontend_domain_aliases` /
  `frontend_acm_certificate_arn` ready for when a real domain is attached
  to the frontend; the API distribution would need the same treatment.
- **RDS backups**: 7-day retention, no final snapshot on destroy
  (`skip_final_snapshot = true`) — fine for now, reconsider once this holds
  data you can't regenerate.
