# Deploying: GitHub Pages (frontend) + Render/Upstash/R2 (backend)

GitHub itself has no product that can run the API, Postgres, Redis, or file
storage — GitHub Pages only serves static files. This is the split that
lets the frontend genuinely live on GitHub for free, with everything
stateful hosted on free tiers elsewhere:

| Piece                     | Host                                     |
| ------------------------- | ----------------------------------------- |
| Frontend (static export)  | GitHub Pages                              |
| API                       | Render (free web service, Docker)         |
| Postgres                  | Render (free database)                    |
| Redis (BullMQ)            | Upstash (free)                            |
| File storage (S3-compat.) | Cloudflare R2 (free tier, no code changes) |

**Read this whole doc before starting** — a few steps have to happen in a
specific order (the API needs to exist before you know its URL to give the
frontend; the frontend needs to exist before you know its URL to lock down
CORS on the API).

**Free-tier reality check:** these are genuinely free, but not
production-SLA infrastructure. Render's free web service spins down after
15 minutes of inactivity and takes 30-60s to cold-start on the next
request. Free-tier database policies change over time — check Render's
current terms for the Postgres free tier before treating this as a
permanent home for real data. Fine for a demo, pilot, or internal tool with
low traffic; not a substitute for real production infra if this starts
handling money for real.

## 0. Prerequisites

- A GitHub repo with this code pushed to `main`
- Accounts (all free to create): [Render](https://render.com), [Upstash](https://upstash.com), [Cloudflare](https://dash.cloudflare.com) (for R2)

## 1. Redis — Upstash

1. Create a database at [console.upstash.com](https://console.upstash.com) (any region close to where you'll deploy the API).
2. Copy the **Redis connection string** it gives you (starts with `rediss://`) — this is your `REDIS_URL`.

## 2. File storage — Cloudflare R2

1. In the Cloudflare dashboard, go to **R2** and create a bucket (e.g. `p2p-prod`).
2. **R2 > Manage API Tokens > Create API Token** — grant it read/write access to that bucket. Save the **Access Key ID** and **Secret Access Key** shown once.
3. Note your **Account ID** (shown in the R2 dashboard sidebar) — your endpoint is `https://<account-id>.r2.cloudflarestorage.com`.
4. You now have: `S3_BUCKET` (the bucket name), `S3_REGION=auto`, `S3_ENDPOINT` (the URL above), `AWS_ACCESS_KEY_ID`, `AWS_SECRET_ACCESS_KEY`.

No code changes needed — `StorageService` already speaks the S3 API and R2 is S3-compatible; it just needed `S3_ENDPOINT` support, which is already in place.

## 3. API + Postgres — Render

1. In the Render dashboard: **New > Blueprint**, point it at this GitHub repo. Render reads `render.yaml` at the repo root and creates the `p2p-api` web service (built from `apps/api/Dockerfile`) and a `p2p-postgres` free database together.
2. Once created, open the `p2p-api` service → **Environment** tab and fill in the variables `render.yaml` left blank (it can't safely guess these):
   - `REDIS_URL` → from step 1
   - `S3_BUCKET`, `S3_REGION`, `S3_ENDPOINT`, `AWS_ACCESS_KEY_ID`, `AWS_SECRET_ACCESS_KEY` → from step 2
   - `CORS_ALLOWED_ORIGINS` → leave blank for now, come back after step 4
   - `AUTH_JWT_SECRET` was already auto-generated by the blueprint — leave it as-is
3. Deploy. Render builds `apps/api/Dockerfile` and starts the container, which runs `prisma migrate deploy` automatically on every boot before serving traffic.
4. Note the service's public URL (`https://p2p-api-xxxx.onrender.com` or your custom name) — this is your `NEXT_PUBLIC_API_URL` for the frontend.
5. **Seed data is optional and demo-only.** `pnpm --filter api run db:seed` creates 7 users sharing the password `Passw0rd!`, printed to the console — fine for a demo/pilot, but never run this against an environment with real users or data. To run it once against the Render database, use Render's shell (service → **Shell** tab) or run it locally with `DATABASE_URL` temporarily pointed at the Render Postgres connection string.

## 4. Frontend — GitHub Pages

1. In the GitHub repo: **Settings > Pages** → set **Source** to "GitHub Actions" (not "Deploy from a branch").
2. **Settings > Secrets and variables > Actions > Variables** → add a repository variable `NEXT_PUBLIC_API_URL` set to the Render URL from step 3.4.
3. Push to `main` (or run the "Deploy frontend to GitHub Pages" workflow manually from the Actions tab) — `.github/workflows/deploy-pages.yml` builds the static export and publishes it.
4. Your site is live at `https://<your-github-username>.github.io/<repo-name>/`.

## 5. Close the loop — lock down CORS

Now that you know the Pages URL, go back to Render → `p2p-api` → **Environment** and set:

```
CORS_ALLOWED_ORIGINS=https://<your-github-username>.github.io
```

Redeploy the API for this to take effect. Until this is set, the API accepts requests from any origin (fine for initial testing, not for anything real).

## 6. Verify

1. Visit the Pages URL — it should redirect to `/login`.
2. If you seeded demo data, log in as `admin@demo.p2p` / `Passw0rd!`.
3. Expect the first request to be slow (Render's free tier cold start) — that's normal, not a bug.

## Custom domain / repo name changes

If you rename the GitHub repo or move to a custom domain fronting Pages,
update `NEXT_BASE_PATH` in `.github/workflows/deploy-pages.yml` (it currently
derives this automatically from the repo name — a custom domain serving
from the root needs `NEXT_BASE_PATH=` empty instead) and redeploy.

## What's still worth doing before real users depend on this

- Rate limiting exists on `/auth/login` (5/min/IP) but there's still no
  password-reset flow — Admin has to set a new password by hand today.
- No monitoring/error tracking (e.g. Sentry) wired in.
- Free-tier cold starts and database retention limits — see the reality
  check at the top of this doc.
